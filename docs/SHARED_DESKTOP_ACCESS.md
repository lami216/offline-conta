# Windows establishment access — source review

Current correction: **0.1.21**, based on the reviewed 0.1.20 commit `678b7ec788088422ec2b897d7927748c4c6a5aec`, tree `246e7fa87253076225001686483932754fa14736`. Product/app identity, data paths, existing keys, installed licenses, clocks and local accounting schema are preserved. This update restores the original Windows manual activation start screen and unifies credentials in the existing login form.

## Two explicit workspaces

The existing `/` local application retains the original device-code and manual license-file controls when unlicensed, with an optional **Sign in** link to `/login`. It never requests accounting bootstrap data before the local license gate. An already licensed local installation keeps the normal local-account path. There is one ordinary username/password form at `/login`; `/remote-access` is only a compatibility redirect to it, not another account page. There is no visible type selector, phone-activation guide, number-pattern hint, new-organization form or separate establishment-login page.

Local credentials are checked first. A known active local username with a bad password, or a known inactive username, stays local and is never uploaded to the service. The existing local-login JSON/status contract is retained; a same-origin UI-only response header distinguishes truly unknown usernames from inactive accounts. Numeric local usernames support Arabic/Persian digits before considering a remote request, so an already activated numeric account remains usable offline.

For an unknown local identifier, an internal eight-digit 2/3/4-leading number routes to the existing one-device activation request only after explicit generic network consent. This route is not advertised in entry labels or instructions. It never creates an establishment. Other arbitrary identifiers produce the generic instruction to obtain credentials from the institution administrator, with no native remote-entry call. Administrator-created email credentials use the existing organization authentication protocol; a correct new device gets only the pending notice inline in the same form and must explicitly sign in again after approval. No central password is stored or replayed in the background. Approved organization credentials open `/shared`, the financial workspace, directly.

After the original signed, device-bound activation is verified and durably installed, a main-process-only local setup callback may prepare the phone/code as local credentials for a fresh installation. The callback requires the exact current installed document hash and a valid local license; its endpoint rejects browser Origin/cookies and missing or wrong native tokens. The local SQLite write transaction creates a normal first user with the existing full local capabilities only when there are no users and no preexisting accounting/import/audit/settings data or nonzero/custom accounts. Any existing active/inactive accounts or userless ledger remain untouched. Matching retries preserve the original user id, password hash and timestamps. The request's accepted-local grant hash is durably saved before setup; a lost callback/ACK can retry without reinstalling the license clock or selecting another request. The renderer then uses its current typed credentials with the original local-login endpoint to obtain the normal local cookie; no native session/password is returned to the renderer.

`/shared` remains the online financial workspace: central product creation, sales/purchases, inventory and permitted documents. It does not claim full UI parity with every legacy bank/report/edit screen. Local and central data remain separate, with no copy, conversion or merge. Linking the device to an establishment does not change its local license or automatically switch authority; the user separately enters establishment credentials. Returning locally retains the original local account and cookie.

The central organization/branch/member UUIDs and product/party/account/warehouse/document global IDs remain authoritative. Windows uses the existing HTTPS semantic accounting reducer, not a shared SQLite file or a second ledger. The client constructs no profit or cost-at-sale claims; the server applies current stock, rounding, settlement, authorization and cost rules. A sales-only user receives the negotiated server sales projection and cannot retrieve full financial history through this client. Existing local login does not grant central rights.

## Trust, requests and activation

Windows has its own `mr.alkarna.desktop` application identity and `/api/desktop/access/v1/challenge|dispatch` namespace. The proof message is canonical JSON, P-256/SHA-256 IEEE-P1363, bound to path, method, operation, installation and payload/session hashes. HTTPS origin and service public keys are fixed in `desktop/shared-access/public-config.json`, matching the owner-approved Android public configuration. There is no arbitrary URL or imported private key API.

The request sends a Mauritanian number, private request code, app version, meaningful device name, stable installation UUID, public proof key and the existing AKD activation code. An existing signed license is sent for preservation/review when present. Explicit consent precedes network registration. No accounting database, file list, raw MachineGuid, IMEI, local password or service-admin password is sent. The number is not the AKD code and does not automatically link a customer. The service owner explicitly chooses trusted organization/branch/member IDs and reviews identity and quotas. Request code and central employee login are different credentials.

Purposes are `shared`, `activation`, or `both`. The signed `contatools-desktop-decision` binds request purpose, request/installation/key fingerprint/device code, approved IDs, exact license-document hash and delivery lifetime. Windows verifies and durably saves the grant before `request.accept` acknowledges its exact canonical hash. Lost responses retry the same request/grant. Waiting/rejected/expired/approved/linked states are shown; visible-page polling is not push. A rejected request can explicitly prepare another request for owner review. The new entry form always requests phone activation, without a purpose picker or a separate user-initiated shared-link request. Older saved `shared`/`both` requests remain readable and deliverable for compatibility. An already delivered approved grant is finished when the login form opens; a pending phone request refreshes on the next explicit credential submission. An interrupted delivery can be retried without a separate activation page. Only minimal nonsecret request metadata is archived; drafts and license clocks are preserved. There is no automatic new request or term extension. Expired delivery needs owner redelivery of the exact same license, not a replacement license request.

The owner explicitly approved additive trust in the **existing** Contatools service issuer for direct Windows activation. Existing `alkarna-license-v1/v2` pins and verification remain. Only fixed configured service IDs may additionally verify the existing v2 `edition:desktop`, single-install format under `contatools-online-v2:<kid>`. No issuer/key rotation or alternative license clock is introduced. Serialized remote installation verifies the exact document and recognizes an identical already-installed hash without calling the consuming install path again; a consumed/expired clock is never restarted by redelivery. Shared approval alone does not create a Windows offline license. Approved online establishment access does not require a separate local Windows license and cannot unlock the local ledger. The original local bootstrap/command/license and login paths remain unchanged.

## Every new online device requires owner approval

The client negotiates `clientProtocol.deviceApprovalVersion:1`. `session.login` first authenticates the administrator-created account and proves the current installation key. An unknown device receives HTTP 200 with **exactly** five fields: `stage:pending`, `mode:online`, `deviceStatus:pending`, its exact `installationId`, and a stable UUID `requestId`. No token, entitlement, establishment/member/branch details, or accounting data accompanies this response. Windows accepts no additional fields or foreign installation. Only this nonsecret notice and identifier are saved; the central password is not persisted or retried in the background. The user must explicitly enter the credentials again after owner approval.

Approved central entitlements must contain signed `deviceApproval:approved` and the existing exact installation/key/establishment/member/rights/branch bindings. A valid old service signature without the approval marker is refused. The backend must be updated first; an older automatically admitting backend cannot silently bypass this new client contract. Rejected or revoked devices are not automatically re-enrolled. Server authorization remains required on every shared operation.

The owner may later bind an already known standalone Windows installation/key to an establishment and member. The user then enters the separately issued email/password; a phone activation secret never becomes an organization password. This does not reinstall a license, restart a temporary period, alter the local ledger, or move local/tenant drafts. Pending commands and unacknowledged receipts retain their original establishment/member binding and block switching to a different owner. A phone request displays an establishment assignment only when covered by its verified signed decision; unsigned response metadata cannot become a conversion notice. The user confirmed keeping these financial datasets separate; financial migration is not part of this follow-up.

## Windows security and persistence

The installation private key, request secret, session and financial pending intent live only in Electron main, under `userData/shared-access/desktop-access-v1.enc`, encrypted using Electron safeStorage/Windows DPAPI. Insecure/unavailable storage or corrupt state fails closed instead of regenerating identity or writing plaintext. Atomic temporary-file write and fsync precede network submission. A main-process-only loopback token permits the separate local license metadata/install API; cookies and browser Origin are refused there. This token, the proof private key and native session are never exposed to renderer.

Preload exposes narrow methods; access IPC requires the owning BrowserWindow's exact main frame, exact loopback origin and `/remote-access` or `/shared` path. Context isolation, sandbox and disabled Node integration remain. DPAPI protects ordinary files against another OS user's casual access; it is not an uncopyable physical identity and cannot defeat administrator/process compromise or coordinated profile restoration. No production secrets are in source.

## Shared reads, drafts and receipts

Negotiation uses `sharedDeltaVersion:1`, `salesViewVersion:1`, `deviceApprovalVersion:1` and `viewVersion:1`. Initial reads obtain an atomic state/cursor/epoch/view hash. Subsequent reads verify scoped contiguous patches, exact before/after hashes, entity order and final cursor. Gaps, changed epochs, retention misses or validation failures trigger a fresh authoritative bootstrap, not an assumed cursor. Snapshots remain in RAM and never replace local accounting.

Visible polling waits 10 seconds when idle or 20 while editing, plus bounded jitter; background polling stops. One shared read/write uses two service HTTP requests (challenge then dispatch), plus the local loopback license check; no redundant service status preflight is added. The server rechecks authorization during every operation. Timers do not modify license clocks. Polling updates the data view, not editor fields. Drafts are encrypted locally after a 500ms debounce and isolated by organization, central member and branch; logout/reassignment cannot expose another member's draft. A branch switch first durably flushes the current editor, pauses autosave and editing, reads only the selected branch's scoped draft through trusted native IPC, then restores that draft or a clean editor. A failed scoped read keeps the current branch and its fields; last-second edits and other branches' saved drafts are preserved. A complete submitted intent is persisted before network even if that draft debounce has not fired. Offline drafts are never posted as local sales or automatically merged.

New entity creation omits an absent `expectedVersion`; explicit versions, including zero, remain unchanged. Previously saved commands are retried byte-for-byte without rewriting their UUID, payload or hash. One independent financial action has one durable operation UUID/hash. A lost response or restart retries that same action. A server receipt is persisted before display and remains until explicit UI ACK; a later delta failure does not undo a confirmed sale. Another member/organization cannot adopt an unresolved intent or receipt. Unrelated sales are not batched into one accounting transaction. Rejected/conflicted intents need review; a new UUID is not an automatic conflict workaround. Native requests honor numeric or HTTP-date Retry-After on429/503, scoped to the affected operation so pending-registration backoff does not stall sales. Background registration polling adds bounded exponential backoff and jitter while retaining its existing request.
