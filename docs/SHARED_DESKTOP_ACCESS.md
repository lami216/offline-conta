## Two explicit workspaces

The existing `/` local application retains every local capability and its original local accounts and offline activation. New `/remote-access` is a separate page available from login and the current activation page before activation. New `/shared` is the online establishment workspace: central product creation, sales and purchases (cash or full credit), inventory and permitted document reads. It does not claim complete UI parity with every legacy bank/report/edit screen. Local data is never automatically copied, converted or merged. A separate reviewed migration is needed to import a first local source; this release does not perform one.

The central organization/branch/member UUIDs and product/party/account/warehouse/document global IDs remain authoritative. Windows uses the existing HTTPS semantic accounting reducer, not a shared SQLite file or a second ledger. The client constructs no profit or cost-at-sale claims; the server applies current stock, rounding, settlement, authorization and cost rules. A sales-only user receives the negotiated server sales projection and cannot retrieve full financial history through this client. Existing local login does not grant central rights.

## Trust, requests and activation

Windows has its own `mr.alkarna.desktop` application identity and `/api/desktop/access/v1/challenge|dispatch` namespace. The proof message is canonical JSON, P-256/SHA-256 IEEE-P1363, bound to path, method, operation, installation and payload/session hashes. HTTPS origin and service public keys are fixed in `desktop/shared-access/public-config.json`, matching the owner-approved Android public configuration. There is no arbitrary URL or imported private key API.

The request sends a Mauritanian number, private request code, app version, meaningful device name, stable installation UUID, public proof key and the existing AKD activation code. An existing signed license is sent for preservation/review when present. Explicit consent precedes network registration. No accounting database, file list, raw MachineGuid, IMEI, local password or service-admin password is sent. The number is not the AKD code and does not automatically link a customer. The service owner explicitly chooses trusted organization/branch/member IDs and reviews identity and quotas. Request code and central employee login are different credentials.

Purposes are `shared`, `activation`, or `both`. The signed `contatools-desktop-decision` binds request purpose, request/installation/key fingerprint/device code, approved IDs, exact license-document hash and delivery lifetime. Windows verifies and durably saves the grant before `request.accept` acknowledges its exact canonical hash. Lost responses retry the same request/grant. Waiting/rejected/expired/approved/linked states are shown; visible-page polling is not push. Rejected or expired requests need owner review; the client does not silently create another request or extend a term.

The owner explicitly approved additive trust in the **existing** Contatools service issuer for direct Windows activation. Existing `alkarna-license-v1/v2` pins and verification remain. Only fixed configured service IDs may additionally verify the existing v2 `edition:desktop`, single-install format under `contatools-online-v2:<kid>`. No issuer/key rotation or alternative license clock is introduced. Serialized remote installation verifies the exact document and recognizes an identical already-installed hash without calling the consuming install path again; a consumed/expired clock is never restarted by redelivery. Shared approval alone does not create a Windows license; central login still requires a valid local Windows license.

## Windows security and persistence

The installation private key, request secret, session and financial pending intent live only in Electron main, under `userData/shared-access/desktop-access-v1.enc`, encrypted using Electron safeStorage/Windows DPAPI. Insecure/unavailable storage or corrupt state fails closed instead of regenerating identity or writing plaintext. Atomic temporary-file write and fsync precede network submission. A main-process-only loopback token permits the separate local license metadata/install API; cookies and browser Origin are refused there. This token, the proof private key and native session are never exposed to renderer.

Preload exposes narrow methods; access IPC requires the owning BrowserWindow's exact main frame, exact loopback origin and `/remote-access` or `/shared` path. Context isolation, sandbox and disabled Node integration remain. DPAPI protects ordinary files against another OS user's casual access; it is not an uncopyable physical identity and cannot defeat administrator/process compromise or coordinated profile restoration. No production secrets are in source.

## Shared reads, drafts and receipts

Negotiation uses `sharedDeltaVersion:1`, `salesViewVersion:1` and `viewVersion:1`. Initial reads obtain an atomic state/cursor/epoch/view hash. Subsequent reads verify scoped contiguous patches, exact before/after hashes, entity order and final cursor. Gaps, changed epochs, retention misses or validation failures trigger a fresh authoritative bootstrap, not an assumed cursor. Snapshots remain in RAM and never replace local accounting.

Visible polling waits 10 seconds when idle or 20 while editing, plus bounded jitter; background polling stops. One shared read/write uses two service HTTP requests (challenge then dispatch), plus the local loopback license check; no redundant service status preflight is added. The server rechecks authorization during every operation. Timers do not modify license clocks. Polling updates the data view, not editor fields. Drafts are encrypted locally after a 500ms debounce and isolated by organization, central member and branch; logout/reassignment cannot expose another member's draft. A complete submitted intent is persisted before network even if that draft debounce has not fired. Offline drafts are never posted as local sales or automatically merged.

One independent financial action has one durable operation UUID/hash. A lost response or restart retries that same action. A server receipt is persisted before display and remains until explicit UI ACK; a later delta failure does not undo a confirmed sale. Another member/organization cannot adopt an unresolved intent or receipt. Unrelated sales are not batched into one accounting transaction. Rejected/conflicted intents need review; a new UUID is not an automatic conflict workaround.
